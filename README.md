# Aster — AI Personal Assistant

Aster is a multi-user AI personal assistant built with Next.js. It connects to your apps (Gmail, WhatsApp), summarizes your day into an AI-generated brief, delivers scheduled briefings, and lets you chat with an agent that can pull live data from your connected accounts.

## Features

- **Landing page** — marketing site with hero, features, integrations, how-it-works, and FAQ sections.
- **Authentication** — email/password and Google OAuth sign-in, backed by [InsForge](https://insforge.dev) auth. Multi-user by design; no shared tokens.
- **Dashboard** — "Today's Brief" generated by an AI model from all connected providers, plus stat cards, an activity chart, priority items, and connected-apps overview. Provider data is normalized through a pluggable registry (`lib/server/dashboard/`), with refresh rate-limiting.
- **Gmail integration** — first-party Google OAuth flow (per-user tokens stored server-side), REST endpoints for emails/labels/send, and an MCP endpoint exposing Gmail tools with an in-app tool runner.
- **Google Calendar integration** — the tool catalog comes from Google's **official remote Calendar MCP server** (`calendarmcp.googleapis.com`): tool names, descriptions and JSON Schemas are always fetched live via `tools/list`, never hardcoded. Execution is MCP-first with a REST fallback (see below). Shares one Google grant with Gmail via incremental authorization, so connecting the second app only asks for the new scopes. The Settings page generates a form for each tool from its JSON Schema.
- **Outlook integration** — mail *and* calendar through Microsoft's **official Work IQ MCP servers** (`agent365.svc.cloud.microsoft`, `workiq.svc.cloud.microsoft`). The Settings page shows the union of all three catalogs, fetched live via `tools/list`; there are no Microsoft Graph REST wrappers anywhere in the codebase. Entra OAuth with PKCE, one shared per-user grant, and incremental consent per MCP resource. **Requires a Microsoft 365 work/school account with a Copilot license** — see below.
- **WhatsApp integration** — [Baileys](https://github.com/WhiskeySockets/Baileys) socket with a pairing-code flow (no QR scanning required), DB-backed auth state and message store, status/reconnect/disconnect endpoints, and an MCP endpoint exposing WhatsApp tools.
- **Agent chat ("Aster")** — streaming chat (NDJSON over an OpenAI-compatible Chat Completions API) with a bounded tool loop that calls namespaced Gmail/WhatsApp MCP tools, live status events, follow-up suggestions, and DB-persisted conversations (1-day validity).
- **Briefings** — user-defined scheduled briefings. A single Trigger.dev cron (every 15 minutes) asks the app to atomically claim due runs, then enqueues one generation job per run. Briefing detail pages with categorized items, history, compose, and send.
- **Alerts, Pricing, Settings** pages.

## Getting started

1. **Install dependencies**

   ```bash
   npm install
   ```

2. **Configure environment** — create `.env.local`:

   ```bash
   # InsForge (auth + database)
   NEXT_PUBLIC_INSFORGE_BASE_URL=...
   NEXT_PUBLIC_INSFORGE_ANON_KEY=...
   INSFORGE_ADMIN_API_KEY=...        # server-side user management

   # AI (any OpenAI-compatible endpoint)
   OPENAI_API_KEY=...
   OPENAI_MODEL=gpt-4o-mini          # optional, default gpt-4o-mini
   OPENAI_BASE_URL=...               # optional, e.g. Gemini's OpenAI-compatible URL

   # Gmail + Google Calendar integrations (one Google Cloud OAuth client,
   # shared per-user grant — see "Google setup" below)
   GOOGLE_CLIENT_ID=...
   GOOGLE_CLIENT_SECRET=...

   # Google sign-in — separate OAuth client (openid/email/profile only), so the
   # Gmail client's 100-test-user cap never applies to login.
   GOOGLE_SIGNIN_CLIENT_ID=...     # optional, falls back to GOOGLE_CLIENT_ID
   GOOGLE_SIGNIN_CLIENT_SECRET=... # optional, falls back to GOOGLE_CLIENT_SECRET

   # Outlook integration — Microsoft Entra app (see "Outlook setup" below)
   MICROSOFT_CLIENT_ID=...
   MICROSOFT_CLIENT_SECRET=...

   # OTP signing (email verification, password reset)
   PHONE_AUTH_SECRET=...             # random secret for signing OTP state

   # Internal job endpoints (shared with Trigger.dev)
   INTERNAL_API_SECRET=...
   ```

3. **Run the dev server**

   ```bash
   npm run dev
   ```

   Open [http://localhost:3000](http://localhost:3000).

## Google setup (Gmail + Calendar)

Both Google integrations share **one** OAuth client (`GOOGLE_CLIENT_ID`) and one
per-user grant, so connecting the second app uses incremental authorization and
only asks for the scopes that are still missing. In the Cloud project owning that
client:

1. **Enable the APIs** — Gmail API, plus for Calendar:

   ```bash
   gcloud services enable calendar-json.googleapis.com
   gcloud services enable calendarmcp.googleapis.com   # the remote MCP server
   ```

2. **Add the scopes** to the OAuth consent screen:

   | Integration | Scopes |
   |---|---|
   | Gmail | `gmail.readonly`, `gmail.send`, `gmail.labels` |
   | Calendar | `calendar.events`, `calendar.calendarlist.readonly`, `calendar.events.freebusy` |

3. **Authorized redirect URIs** — one per integration:
   `{origin}/api/integrations/gmail/callback` and
   `{origin}/api/integrations/google-calendar/callback`.

4. **Keep the consent screen in Production**, never Testing — Testing mode expires
   refresh tokens after 7 days, which breaks the scheduled briefing jobs.

Because the grant is shared, disconnecting one Google app does **not** revoke it
while the other is still connected; the tokens are dropped and revoked once the
last Google integration is turned off (`disconnectGoogleProvider`).

### Calendar: MCP-first, REST fallback

`calendarmcp.googleapis.com` is in **Developer Preview** and only executes tools
for Google Workspace accounts enrolled in the preview programme. On a consumer
`@gmail.com` account, `initialize` and `tools/list` succeed but every
`tools/call` returns `The caller does not have permission`.

So Calendar runs in two halves:

| Concern | Source |
|---|---|
| Tool catalog (names, descriptions, JSON Schemas) | Always Google's MCP server — `tools/list` needs no credentials |
| Execution | Google's MCP server when it will serve us, else `google-calendar-rest.ts` |

`google-calendar-rest.ts` implements the same nine tools against the Calendar
REST API, mirroring Google's published input/output schemas exactly, so callers
cannot tell which path served them. A `PERMISSION_DENIED` is cached for an hour
(`DENIED_TTL_MS`) so the wasted round trip happens once, not per call. The
Settings dialog shows which path is live, and an account that becomes eligible
switches to real MCP execution with no code change.

## Outlook setup (Microsoft Work IQ MCP)

Outlook is built entirely on Microsoft's official MCP servers. Nothing in this
integration calls Microsoft Graph directly:

| Server | Endpoint | Contributes |
|---|---|---|
| `mcp_MailTools` | `agent365.svc.cloud.microsoft/agents/tenants/{tid}/servers/mcp_MailTools` | Named mail tools (get, search, send, reply, reply-all, drafts) |
| `mcp_CalendarTools` | `…/servers/mcp_CalendarTools` | Named calendar tools (list, get, create, update, delete, accept/decline, free-busy, find-times) |
| Work IQ (universal) | `workiq.svc.cloud.microsoft/mcp` | Path-based tools (`fetch`, `do_action`, …) covering what the other two omit: mail folders, attachments, forwarding, calendar lists |

### Prerequisites — read before connecting

The protected-resource metadata for all three servers names
`https://login.microsoftonline.com/organizations/v2.0` as the authorization
server. **`organizations`, not `common`** — so:

- **Personal Microsoft accounts (@outlook.com, @hotmail.com) cannot connect.**
  They are rejected by Entra itself, not by this app.
- Each user needs a **Microsoft 365 Copilot license**.
- A tenant admin must **grant admin consent** for the app, and Work IQ must be
  enabled in the tenant.

There is deliberately **no REST fallback** (unlike Google Calendar): an account
Microsoft will not serve is reported with the specific reason — "needs a work
account", "needs a Copilot license", "needs admin consent", "Work IQ not
enabled" — rather than being quietly served by a hand-rolled Graph wrapper.

### Entra app registration — `MICROSOFT_CLIENT_ID` / `MICROSOFT_CLIENT_SECRET`

**Scripted (recommended).** Needs the `Microsoft.Graph` PowerShell module and a
Global Administrator (tenant-wide consent requires it):

```powershell
Install-Module Microsoft.Graph -Scope CurrentUser
./scripts/entra-outlook-setup.ps1 -RedirectUri http://localhost:3000/api/integrations/outlook/callback
```

It provisions the Work IQ service principals, creates a multi-tenant app with
the redirect URI, requests and consents to the delegated permissions, mints a
secret, and prints both values. It is idempotent apart from the secret, which
Entra only ever displays once.

**Manual.** The order matters — step 1 is the one everybody misses:

1. **Provision the Work IQ service principals.** They do not exist in a tenant
   by default, and until they do the APIs are absent from the permission picker
   and sign-in fails with `AADSTS650052`. Create them (Azure CLI shown; the
   `Microsoft.Graph` equivalent is `New-MgServicePrincipal -AppId <id>`):

   ```bash
   az ad sp create --id 16b1878d-62c7-4009-aa25-68989d63bbad   # mcp_MailTools
   az ad sp create --id 910333d2-47e9-43ca-981f-6df2f4531ef4   # mcp_CalendarTools
   az ad sp create --id fdcc1f02-fc51-4226-8753-f668596af7f7   # Work IQ (universal)
   ```

   App IDs are from Microsoft's own
   [Enable-WorkIQToolsForTenant.ps1](https://github.com/microsoft/work-iq/blob/main/scripts/Enable-WorkIQToolsForTenant.ps1).

2. In the [Entra admin center](https://entra.microsoft.com) → **App
   registrations** → **New registration**: name it, choose **Accounts in any
   organizational directory** (multi-tenant), and add a **Web** redirect URI of
   `{origin}/api/integrations/outlook/callback`.
3. **API permissions** → **Add a permission** → **APIs my organization uses** →
   search *Work IQ* → for each of the three servers pick **Delegated
   permissions** and select the offered scope (the MCP servers expose
   `Tools.ListInvoke.All`; the universal server exposes `WorkIQAgent.Ask`). Add
   `openid`, `profile` and `offline_access` from Microsoft Graph.
4. **Grant admin consent for &lt;tenant&gt;** — all three require it.
5. **Certificates & secrets** → **New client secret** → copy the **Value**
   (not the Secret ID) immediately; it is never shown again.
6. Put the Application (client) ID and that value in `.env.local`, then run
   `npm run verify:outlook`.

Redirect URIs must match byte-for-byte, so a deployed instance needs its own
entry (`https://…/api/integrations/outlook/callback`) alongside localhost.

### How the connect flow works

Both the MCP endpoint URLs and their OAuth scopes embed the tenant GUID, which
is unknown until the user signs in — so connecting is two-phase:

1. `/authorize` against `organizations` with `openid profile offline_access`
   and PKCE (S256). The `id_token`'s `tid` claim is the tenant, and
   `preferred_username` the account.
2. The shared refresh token is redeemed **per resource** against `/{tid}/`. Each
   resource's scope is read from its own
   `/.well-known/oauth-protected-resource` document rather than hardcoded, so a
   change to Microsoft's URI scheme needs no code change.

A resource whose permission has not been consented answers `AADSTS65001`, which
sends the user through **one** more `/authorize` for just that scope —
incremental authorization, the direct analogue of Google's
`include_granted_scopes`. When a grant already exists, the account is passed as
`login_hint` with no `prompt`, so Entra reuses the existing session silently.

Mail and Calendar are required to report "Connected"; the universal server is
optional, so declining it still leaves Outlook usable, just without the
gap-filling path tools. Entra exposes no revocation endpoint, and revoking would
mean a Graph call, so **Disconnect** drops the stored tokens — users can revoke
the app itself at <https://myapplications.microsoft.com>.

> Work IQ MCP is in **preview**, and Microsoft warns that tool names and
> parameters may change. Nothing here hardcodes them: the catalog is fetched at
> runtime, and the Settings page's one-click presets are dropped automatically
> unless a tool's published `inputSchema` actually declares the arguments they
> set.

### Verifying the integration

```bash
npm run verify:outlook              # read-only
npm run verify:outlook -- --run-tool  # also executes one read-only calendar query
```

Nine staged checks, each running only if the previous one gave it what it needs
and otherwise printing the exact next step. Stages 1–3 (discovery, scope
derivation, authorize-URL construction, state tampering) need **no** Microsoft
account. Stages 4–9 pick up the first connected user and prove the parts that
cannot be faked: per-resource token acquisition, the live catalog with every
tool's real argument names, coverage of the eighteen intended actions, and a
live tool call.

Stage 7 exists specifically to settle the one assumption that could not be
checked offline — the universal server's path argument name. It prints the real
one and tells you whether the Settings presets will bind or be silently dropped.

## Background jobs (Trigger.dev)

Scheduled briefings run through Trigger.dev (`trigger.config.ts`):

```bash
npm run trigger:dev      # run tasks locally against your dev server
npm run trigger:deploy   # deploy tasks
```

Set these in the Trigger.dev dashboard environment:

- `APP_BASE_URL` — public URL of the deployed app
- `INTERNAL_API_SECRET` — must match the app's value; jobs authenticate to `/api/briefings/claim-due` and `/api/briefings/run` with the `x-internal-secret` header

The scheduler is intentionally thin: one cron tick every 15 minutes claims due briefing runs atomically in the database, then fans out one `briefing-generate` job per run (idempotent per `runId`).

## Deployment notes

- **WhatsApp requires a persistent Node.js process.** The Baileys socket lives in a `globalThis` map, so serverless platforms that freeze/recycle processes will drop the connection. Deploy to a long-running Node host (or a single always-on instance) for reliable WhatsApp connectivity.
- MCP endpoints (`/api/integrations/{gmail,google-calendar,outlook,whatsapp}/mcp`) are consumed by the in-app agent; tools are namespaced per provider (`gmail_search_inbox`, `google-calendar_list_events`, `outlook_mcp_MailTools_graph_mail_sendMail`, …). All four are built from one proxy factory (`lib/server/mcp-proxy.ts`) over a shared streamable-HTTP transport (`lib/server/mcp-http.ts`).
- Gmail and WhatsApp tools are implemented in-app; Google Calendar's and Outlook's are proxied to the vendors' own servers, so their catalogs are fetched at runtime (cached for an hour — per tenant for Outlook) rather than hardcoded.
